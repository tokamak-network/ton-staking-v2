## 🔍 **1. 개요**

본 문서는 `ton-staking-v2/op-e2e` 프로젝트 내에서 **Slashing 관련 테스트**와 **RAT (Realized Attention Token) 관련 테스트**의 차이점을 심층적으로 분석한 보고서입니다. 두 테스트 모듈은 동일한 TON 스테이킹 시스템을 대상으로 하지만, **목적, 테스트 대상 계약, 시나리오, 보안 모델**에서 중요한 차이를 보입니다.

## 🧱 **2. 프로젝트 구조 요약**

```
📁 bindings/                  → Ethereum 스마트 계약의 Go 바인딩 (자동 생성)
📁 e2eutils/rat/             → RAT 시스템 설정 및 유틸리티
📁 faultproofs/              → RAT 기반 부정행위 감지 테스트
📁 slashing/                 → 슬래싱(Slashing) 메커니즘 테스트
📄 go.mod, go.sum            → Go 모듈 종속성
📄 Makefile                  → 테스트 실행 스크립트
📄 README.md                 → 프로젝트 안내
```

- **RAT (Realized Attention Token)**: L2 블록 생성에 대한 주의력(attention)을 측정하고, 부정행위를 증명하는 fault proof 시스템의 핵심 컴포넌트.
- **Slashing**: 검증인(validator)의 악의적 또는 부적절한 행동에 대해 보상을 몰수하는 메커니즘.

## 🔄 **3. RAT 관련 테스트 (faultproofs/)**

### 📍 위치
- `📁 faultproofs/`
  - `rat_system_test.go`
  - `rat_challenge_test.go`
  - `rat_challenge_helpers.go`

### 🎯 목적
RAT 시스템의 **부정행위 증명**(Fault Proof) 메커니즘이 정상적으로 작동하는지 검증.

### ✅ 주요 테스트 항목
| 항목 | 설명 |
|------|------|
| `TestTONStakingSystemStartup` | 시스템 시작 시 모든 핵심 계약 (TON, WTON, RAT, SeigManager 등)이 정상 배포되었는지 확인 |
| `TestSimpleRAT_ValidatorRegistration` | 검증인이 TON을 스테이킹하여 RAT 시스템에 등록되는지 검증 |
| `RAT Dispute Game` | 공격자와 방어자가 클레임을 제기하고, 부정행위를 증명하는 과정 테스트 |

### 🔗 핵심 계약
- `RAT.sol` → 부정행위 감지 및 증명 게임
- `FaultDisputeGame.sol` → 클레임 기반 분쟁 게임 구조
- `TON`, `WTON` → 스테이킹 자산
- `SystemConfig` → L2 시스템 설정

### 🛠 테스트 시나리오 예시
1. 검증인이 50,000 TON을 스테이킹
2. RAT 계약에 등록
3. 잘못된 L2 블록을 제출 (가짜 제안)
4. 다른 검증인이 `attack()`으로 분쟁 제기
5. 분쟁 게임이 시작되고, 최종적으로 악의적 제안자가 슬래싱 대상이 됨

### 📌 특징
- **상태 기반 증명**(State-based fraud proof)
- **분쟁 게임**(Dispute Game) 구조 활용
- **이벤트 중심**: `eventDisputeGameCreated`, `eventAttentionTestTriggered` 모니터링
- **Ethereum L1에서 실행**되며, L2 블록의 무결성을 보장

## ⚔️ **4. Slashing 관련 테스트 (slashing/)**

### 📍 위치
- `📁 slashing/`
  - `slashing_test.go`
  - `slashing_helpers.go`
  - `rat_challenge_helpers.go` (복사본, 중복 코드 주의)

### 🎯 목적
검증인이 **악의적 행동**을 했을 때, **슬래싱**(Slashing)이 정상적으로 수행되는지 검증.

### ✅ 주요 테스트 항목
| 항목 | 설명 |
|------|------|
| `SlashingContracts` 구조체 | 슬래싱 관련 계약들에 대한 연결 |
| `connectSlashingContracts()` | 슬래싱 전용 계약 인스턴스 생성 |
| `slashing_test.go` | 슬래싱 조건 충족 시 보상 몰수 테스트 |

### 🔗 핵심 계약
- `Layer2Manager_Slashing.sol`
- `DepositManager_Slashing.sol`
- `SeigManager_Slashing.sol`
- `DepositManager.sol`
- `Layer2ManagerV11.sol`

> ⚠️ 주의: `_Slashing` 접미어가 붙은 계약은 **슬래싱 전용 뷰 또는 외부 호출 인터페이스**일 수 있음.

### 🛠 테스트 시나리오 예시
1. 검증인이 **이중 서명**(double signing) 또는 **장기간 오프라인** 상태
2. 슬래싱 조건 충족
3. `SeigManager_Slashing`이 보상 몰수 트리거
4. `Layer2Manager_Slashing`이 검증인 상태를 `slashed`로 변경
5. 보상이 몰수되고, 검증인은 더 이상 참여 불가

### 📌 특징
- **행위 기반 처벌**: 검증인의 행동 패턴 분석
- **즉시 슬래싱 또는 지연 슬래싱** 가능
- **다중 레이어 보호**: DepositManager, Layer2Manager, SeigManager에서 각각 슬래싱 로직 구현
- **보상 재분배**: 슬래싱된 보상은 시스템이나 신고자에게 지급될 수 있음

## 🆚 **5. RAT 테스트 vs Slashing 테스트: 비교 분석**

| 항목 | **RAT 테스트** | **Slashing 테스트** |
|------|----------------|---------------------|
| **위치** | `faultproofs/` | `slashing/` |
| **목적** | L2 블록의 **무결성 검증** | 검증인의 **악의적 행동 처벌** |
| **기반 메커니즘** | 분쟁 게임 (Fault Proof) | 슬래싱 (Slashing) |
| **주요 트리거** | 잘못된 상태 제안 | 이중 서명, 오프라인, 부정 행위 |
| **핵심 계약** | `RAT.sol`, `FaultDisputeGame.sol` | `*_Slashing.sol`, `SeigManager` |
| **테스트 방식** | 분쟁 게임 시뮬레이션 | 상태 변경 및 보상 몰수 검증 |
| **시간 지연** | 분쟁 게임은 시간이 소요됨 (on-chain clock) | 즉시 또는 지연된 슬래싱 가능 |
| **보상 처리** | 승리자에게 보상 분배 | 몰수된 보상은 시스템 또는 신고자에게 |
| **의존성** | L2 블록 해시, 시스템 설정 | 검증인 상태, 서명 기록 |
| **테스트 계정** | Validator, Proposer, Challenger | Validator, Slasher (또는 시스템) |
| **사용 라이브러리** | `dispute game`, `claim`, `attack` | `slash()`, `isSlashed()`, `updateState()` |

## ⚠️ **7. 문제점 및 개선 제안**

### 🔄 **1. 코드 중복**
- `faultproofs/rat_challenge_helpers.go`와 `slashing/rat_challenge_helpers.go`가 **거의 동일한 내용**을 포함하고 있음.
- **해결 방안**: 공통 패키지 생성 (예: `e2eutils/testenv/`)에 `TestAccounts`, `setupTestAccounts()` 등을 이전.

### 🔐 **2. 하드코딩된 프라이빗 키**
- 테스트용 프라이빗 키가 소스에 노출됨.
- **해결 방안**: 환경 변수 또는 테스트 전용 키 관리자 사용.

### 🧩 **3. 계약 이름 혼란**
- `Layer2Manager_Slashing`, `SeigManager_Slashing` 등은 **슬래싱 전용 뷰 계약**인지, **슬래싱 로직 계약**인지 명확하지 않음.
- **해결 방안**: 문서화 또는 주석 추가.

### 📈 **4. 테스트 범위 제한**
- 현재 테스트는 **기본 등록 및 슬래싱 확인**에 그침. 실제 공격 시나리오 (이중 서명, 상태 조작) 부족.
- **개선 제안**: 더 복잡한 공격 시나리오 추가 (예: MEV, 장기간 오프라인 시뮬레이션).

## 📚 **8. 결론**

| 요약 | 설명 |
|------|------|
| **RAT 테스트** | **L2 블록의 정확성**을 보장하는 **부정행위 증명 시스템**을 검증. 분쟁 게임을 통해 잘못된 제안을 감지하고 대응. |
| **Slashing 테스트** | **검증인의 신뢰성**을 보장하는 **행위 기반 처벌 시스템**을 검증. 악의적 행동 시 보상 몰수. |
| **관계** | RAT 시스템에서 분쟁 게임에서 패배한 검증인은 **슬래싱의 대상**이 됨 → 두 시스템은 **연계되어 있음**. |

> ✅ **핵심 인사이트**:  
> - **RAT는 "무엇이 잘못되었는가?"** 를 판단하고,  
> - **Slashing은 "누가 책임이 있는가?"** 에 대해 처벌한다.  
> → 두 시스템은 **보완적 관계**이며, Together가 되어 **안전한 L2 운영**을 보장.
