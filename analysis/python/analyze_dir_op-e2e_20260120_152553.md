## 1) 프로젝트 관점에서의 큰 그림

이 저장소는 Go 기반의 E2E 테스트 묶음이며, 핵심은 다음 2가지 축으로 나뉩니다.

1. **RAT 관련 테스트 (package `faultproofs`)**
   - “Validator 등록/활성화”, 그리고 “Fault Proof(DisputeGame 등)와 연동되는 RAT 행위”를 검증하려는 성격
   - 시스템이 정상 기동되고(RAT/TON/WTON/SeigManager 등 배포 확인), RAT의 기본 플로우가 동작하는지 확인

2. **Slashing 관련 테스트 (package `slashing`)**
   - “규칙 위반/조건 충족 시 벌점(슬래싱)이 발생하는지”, 즉 **처벌 메커니즘**이 제대로 동작하는지를 검증하려는 성격
   - Slashing 전용/확장 컨트랙트 바인딩(`*Slashing`)을 통해 DepositManager/Layer2Manager/SeigManager의 슬래싱 기능을 직접 테스트

두 테스트 모두 `e2eutils/rat.StartTONStakingSystem(t)`로 동일한 E2E 시스템(로컬 체인/배포된 컨트랙트 세트)을 띄운 뒤, 각기 다른 도메인을 검증합니다.

## 3) RAT 관련 테스트(`faultproofs` 패키지)의 목적과 특징

### 3.1 목적(무엇을 확인하나)
RAT 테스트는 “정상적인 참여자(validator)가 시스템에 진입하고 활동 상태가 되는가”를 우선 검증합니다.

예시: `faultproofs/rat_challenge_test.go`의 `TestSimpleRAT_ValidatorRegistration`
- TON 잔고 확인
- (필요 시) 최소 담보(min collateral) 조건 조정
- TON을 사용해 validator 등록 수행
- 최종적으로 `RAT.IsValidatorActive(...) == true`를 확인

즉, **기본 플로우의 성공(등록/활성화)**이 핵심입니다.

### 3.2 주요 컨트랙트 의존성
RAT 테스트에서 직접적으로 다루는 컨트랙트 인스턴스는 비교적 단순합니다.
- `RAT` (`bindings.RAT`)
- `TON` (`bindings.ERC20`)  
(필요 시 WTON 등도 시스템 기동 검증에서 간접 확인)

또한 DisputeGame 관련 상수/ABI 사용 흔적이 보이며(`abi`, `ethereum` import, 이벤트 시그니처), RAT이 fault proof 이벤트/게임과 상호작용하는 시나리오(도전/챌린지)로 확장되는 테스트 성격을 암시합니다. (현재 발췌 코드에서는 “등록”이 대표)

### 3.3 성공 조건의 성격
- “정상 동작” 확인: 등록되었는가? active 상태인가?
- 주로 상태 조회(read)로 성공 여부를 단정
  - `IsValidatorActive(...)` 같은 뷰 함수 중심

## 4) Slashing 관련 테스트(`slashing` 패키지)의 목적과 특징

### 4.1 목적(무엇을 확인하나)
Slashing 테스트는 **“처벌 기능이 올바르게 트리거되고 결과가 반영되는지”**에 초점이 있습니다.

등록/활성화 자체보다,
- 어떤 조건(예: L2 관련 조건, DisputeGame 발생, AttentionTest 등)을 만족했을 때
- Deposit/Seig/Layer2 관련 상태가 슬래싱 로직에 의해 변경되는지
를 보는 방향입니다.

### 4.2 주요 컨트랙트 의존성(차이가 가장 큰 지점)
Slashing 테스트는 **슬래싱 전용 바인딩**을 핵심으로 씁니다.

`slashing/slashing_helpers.go`의 `connectSlashingContracts`가 명확히 보여주는 대상:
- `Layer2ManagerSlashing` (`bindings.Layer2ManagerSlashing`)
- `DepositManagerSlashing` (`bindings.DepositManagerSlashing`)
- `SeigManagerSlashing` (`bindings.SeigManagerSlashing`)
- + 비교/호환을 위해 원본도 함께 연결
  - `DepositManager` (`bindings.DepositManager`)
  - `Layer2ManagerV11` (`bindings.Layer2ManagerV11`)

즉, RAT 테스트가 “참여(등록)”를 직접 만지는 편이라면, Slashing 테스트는 **운영/검증/처벌에 필요한 매니저 계열(Deposit/Seig/Layer2)**을 더 폭넓게 만집니다.

### 4.3 성공 조건의 성격
- “정상 행위”의 성공이 아니라, **위반/조건 충족 → 패널티 반영**의 검증이 중심이 됩니다.
- 보통 아래와 같은 유형의 체크가 뒤따를 가능성이 큽니다(프로젝트 의도 상):
  - 특정 계정/밸리데이터의 상태 변화(활성→비활성, 담보 감소 등)
  - 매니저 컨트랙트 내부 슬래시 플래그/카운터/누적량 변화
  - 이벤트 발생 여부(슬래싱 이벤트/DisputeGameCreated/AttentionTestTriggered 등)

## 5) RAT 테스트 vs Slashing 테스트 차이 요약 표

| 구분 | RAT 테스트 (`faultproofs`) | Slashing 테스트 (`slashing`) |
|---|---|---|
| 1차 목적 | **시스템 참여/정상 플로우** 검증(예: validator 등록, active 상태 확인) | **처벌(슬래싱) 메커니즘** 검증(조건 충족 시 패널티 반영) |
| 테스트 성격 | “Happy path” 중심(정상 등록/활성화) + fault proof 연동 시나리오로 확장 여지 | “Adversarial/Policy enforcement” 성격(위반/이상상황 처리) |
| 주요 컨트랙트 | `RAT`, `TON(ERC20)` 중심 | `Layer2ManagerSlashing`, `DepositManagerSlashing`, `SeigManagerSlashing` + 원본 매니저 컨트랙트 병행 |
| 검증 포인트 | `IsValidatorActive` 같은 상태 조회로 성공 단정 | 슬래싱 로직 실행 후 **상태 변화/이벤트/패널티 결과** 확인 |
| 코드 구조 특징 | `rat_system_test.go`처럼 “기동 스모크 테스트”가 동반됨 | `connectSlashingContracts`처럼 “슬래싱 전용 컨트랙트 묶음” 연결이 핵심 유틸로 존재 |
| 중복/공유 | 계정/상수/이벤트 시그니처가 slashing과 유사(중복 구현) | 동일(helpers 파일이 사실상 복제 형태) |

## 6) 코드 관점에서 드러나는 추가 인사이트(유지보수/개선 포인트)

1. **helpers 중복**
   - `faultproofs/rat_challenge_helpers.go`와 `slashing/rat_challenge_helpers.go`가 거의 동일한 역할을 수행하는 것으로 보입니다.
   - 공통 모듈(`e2eutils/common` 같은 패키지)로 분리하면:
     - 테스트 계정/체인ID/TransactOpts 구성 코드 중복 제거
     - 상수(이벤트 시그니처, deposit amount) 단일화 가능

2. **테스트 레이어의 역할 분리 명확**
   - `faultproofs`는 “등록/활성/챌린지(DisputeGame 연동 가능)”를 담당
   - `slashing`은 “처벌 집행(매니저/슬래싱 바인딩)”을 담당  
   이 분리는 도메인적으로 타당하며, 향후 문서/README에도 이 구분을 명시하면 온보딩이 쉬워집니다.
