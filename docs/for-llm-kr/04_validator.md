# 검증자 (Validator)

## 1. 개요

Tokamak Network V3에서 검증자(Validator)는 L2 배치의 유효성을 검증하고 네트워크 보안에 기여하는 역할을 합니다. 검증자는 RAT(Randomized Attention Test)에 응답하여 활성 상태를 증명하고, 그 대가로 시뇨리지의 일부를 보상으로 받습니다.

### 1.1 SystemConfig별 검증자 등록

TON V3에서는 여러 L2가 존재하므로, 검증자는 **특정 L2(SystemConfig)에 개별적으로 등록**합니다.

```
검증자 A ──┬──→ Titan SystemConfig 등록 (담보금 5,000 WTON)
           └──→ Thanos SystemConfig 등록 (담보금 3,000 WTON)

검증자 B ──────→ Titan SystemConfig만 등록 (담보금 10,000 WTON)

검증자 C ──────→ Thanos SystemConfig만 등록 (담보금 2,000 WTON)
```

**SystemConfig를 키로 사용하는 이유:**
- 각 L2는 고유한 SystemConfig(롤업 컨피그) 주소를 가짐
- Layer2Manager에서 SystemConfig로 L2 식별 가능
- L2 입장에서는 자체 SystemConfig 주소를 알고 있음

## 2. 검증자 vs 챌린저 vs 시퀀서

### 2.1 역할 비교

| 구분 | 시퀀서 (Sequencer) | 검증자 (Validator) | 챌린저 (Challenger) |
|------|-------------------|-------------------|---------------------|
| **역할** | L2 트랜잭션 순서 결정 및 배치 제출 | L2 배치 검증 및 RAT 응답 | Fraud proof 제출 |
| **담보금** | 스테이킹 금액 (S_i) | 별도 예치 (D_validator) | 게임에 본드예치 |
| **보상 원천** | 시뇨리지 (1-α)·Seig_i | 시뇨리지 α·y(x)/n | 슬래싱된 시퀀서 담보금 |
| **보상 조건** | L2 운영 및 자격 조건 충족 | RAT 응답 및 활성 상태 유지 | Fraud proof 성공 |
| **슬래싱 조건** | Fraud 발생 | RAT 미응답 | 없음 |
| **리스크** | Fraud 시 전체 담보금 슬래싱 | 미응답 시 C_off 슬래싱 | 실패 시 가스비 손실/게임 본드 손실 |

### 2.2 검증자의 핵심 책임

1. **L2 배치 모니터링**: 시퀀서가 제출한 배치의 유효성 확인
2. **RAT 응답**: 프로토콜이 발행하는 무작위 테스트에 시간 내 응답 (담보금 유지 필수)
3. **Fraud 발견 시 챌린지**: 잘못된 배치 발견 시 fraud proof 제출

### 2.3 검증자 겸 챌린저

검증자는 챌린저 역할을 겸할 수 있습니다. 이 경우 **두 가지 책임을 모두 수행**해야 합니다:

```
시퀀서가 잘못된 배치 제출
            │
            ▼
┌───────────────────────────────────────────────────────────────┐
│  검증자 (챌린저 겸임)                                          │
│                                                               │
│  1. Fraud proof 제출 → 챌린저 보상 (C_max + Δ/n) 획득         │
│                                                               │
│  2. RAT 응답 유지 → 검증자 담보금 보호                         │
│     (RAT 미응답 시 담보금(C_off) 손실)                              │
└───────────────────────────────────────────────────────────────┘
```

**RAT 응답 방법:**
- **submitEvidence**: 직접 증거 제출
- **resolveClaim**: 챌린지 승리 (fraud proof 성공)

두 방법 모두 RAT 응답으로 인정되어 담보금이 복구됩니다.

| 상황 | Fraud Proof | RAT 응답 방법 | 결과 |
|------|-------------|--------------|------|
| 정상 운영 | - | submitEvidence | 검증자 보상 수령 |
| 챌린지 성공 | ✅ 성공 | resolveClaim | 챌린저 보상 + 검증자 보상 |
| RAT 미응답 | - | ❌ | 검증자 담보금(C_off) 손실 |

## 3. 검증자 등록 조건

### 3.1 검증자 최대 수 (N_max = H_max)

**백서 공식 (1)**에서 시퀀서 담보금은 최대 챌린저 수(H_max)를 기준으로 계산됩니다:

```
D_sequencer = H_max · C_max + Δ_sequencer
```

Tokamak Network V3에서 **검증자 = 챌린저**이므로, 모든 검증자가 fraud proof를 제출할 경우를 대비해야 합니다:

```
검증자 최대 수 (N_max) = 최대 챌린저 수 (H_max)
```

| 파라미터 | 설명 | 관계 |
|---------|------|------|
| **H_max** | 최대 동시 챌린저 수 (백서 정의) | 프로토콜 상수 |
| **N_max** | 검증자 최대 등록 수 | N_max = H_max |

### 3.2 검증자 슬롯 관리

```
┌─────────────────────────────────────────────────────────────┐
│  검증자 등록                                                 │
│  - activeValidatorCount < maxValidators (= H_max) 확인      │
│  - 슬롯 확보 → 등록 성공                                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  RAT 슬래싱 발생 (잔액 < D_min 시)                            │
│  - C_off 몰수 → 잔액 < D_min → 비활성화                      │
│  - activeValidatorCount 감소 → 슬롯 해제                     │
└─────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
┌─────────────────────────┐       ┌─────────────────────────┐
│  제거된 검증자 재등록     │       │  새 검증자 등록 시도      │
│                         │       │                         │
│  - D_min 이상 되도록     │       │  - 빈 슬롯 있으면 등록    │
│    담보금 추가           │       │  - 슬롯 없으면 실패       │
│  - 슬롯 있으면 등록 가능  │       │                         │
└─────────────────────────┘       └─────────────────────────┘
```

### 3.3 최소 담보금 및 슬래싱 페널티

**백서 V2 공식 (3), (4), (5)**에 따른 검증자 담보금:

```
c_m ≤ (π_a / N) · C_off               ... (3) RAT 균형 조건
C_off ≥ (c_m · N) / π_a               ... (4) 최소 슬래싱 페널티
D_validator = C_off + Δ_validator      ... (5) 실제 담보금
```

| 파라미터 | 백서 명시 | 설명 |
|---------|----------|------|
| **c_m** | ✅ | 에폭당 attentiveness 유지 비용 |
| **N** | ✅ | 검증자 수 |
| **π_a** | ✅ | RAT 트리거 확률 |
| **C_off** | ✅ | 오프라인 시 슬래싱 페널티 |
| **Δ_validator** | ✅ | 검증자가 제공하는 추가 담보금 (선택적) |
| **D_min** | ✅ | 최소 담보금 임계값 (C_off 이상) |

**공식 (3)의 의미:**
- 오프라인 상태의 예상 페널티 `(π_a/N) · C_off`가 유지 비용 `c_m`보다 커야 함
- 이 조건이 충족되면 attentive 상태 유지가 dominant strategy

### 3.4 선차감-복구 메커니즘 (C_off 기반)

TON V3 RAT는 **C_off 기반 선차감-복구 메커니즘**을 사용합니다:

```
검증자 A @ Titan SystemConfig: 10,000 WTON 스테이킹 (C_off = 2,000, D_min = 3,000)
    │
    ├─ RAT 테스트 트리거 → C_off(2,000 WTON) 선차감 → 잔액 8,000 WTON
    │   └─ 증거 제출 성공 → 2,000 WTON 복구 → 잔액 10,000 WTON
    │
    ├─ RAT 테스트 트리거 → C_off(2,000 WTON) 선차감 → 잔액 8,000 WTON
    │   └─ 미응답 → C_off 몰수 확정 → 잔액 8,000 WTON (D_min 이상이므로 활성 유지)
    │
    ├─ [여러 번 미응답 후] 잔액 2,500 WTON
    │   └─ RAT 미응답 → C_off 몰수 → 잔액 500 WTON (D_min 미만)
    │       └─ 즉시 활성 검증자 세트에서 제거 (잔액은 클레임 가능)
```

**메커니즘 특징 (백서 V2):**
- RAT 트리거 시 **C_off**만 선차감됨 (전체 담보금이 아님)
- 증거 제출 성공 시 C_off 복구
- 미응답 시 C_off 몰수, 잔액이 **D_min 미만**이면 **즉시 활성 검증자 세트에서 제거**
- 제거된 검증자는 잔액을 클레임하여 출금 가능 (재등록 시 D_min 이상 되도록 추가 예치 필요)

### 3.5 기술적 요구사항

| 요구사항 | 설명 |
|---------|------|
| **노드 운영** | 등록한 L2(SystemConfig)의 배치를 모니터링할 수 있는 노드 운영 |
| **24/7 가용성** | RAT 응답 윈도우(~24시간) 내 응답 가능해야 함 |
| **WTON 보유** | 최소 담보금 이상의 WTON 필요 |
| **이더리움 주소** | 검증자 등록 및 보상 수령용 EOA 또는 컨트랙트 |

### 3.6 누가 검증자가 될 수 있나?

- **제한 없음**: 최소 담보금만 충족하면 누구나 등록 가능
- **허가 불필요**: 프로토콜 승인 없이 자유롭게 참여/탈퇴
- **복수 L2 등록 가능**: 하나의 주소가 **여러 L2(SystemConfig)에 등록** 가능
- **L2별 독립적 담보금**: 각 L2에 RAT을 통해 별도의 담보금 예치

                              ▼

│  5. 검증 활동 시작                                           │
│     - 해당 L2(SystemConfig) 배치 모니터링                     │

### 4.2 검증자 등록 (사용자 관점)

TON의 `approveAndCall`을 사용하여 **한 번의 트랜잭션**으로 검증자 등록을 처리합니다.

```solidity
// data = [RAT 주소 32바이트][SystemConfig 주소 32바이트]
bytes memory data = abi.encodePacked(
    bytes32(uint256(uint160(ratContractAddress))),
    bytes32(uint256(uint160(titanSystemConfig)))
);

// TON.approveAndCall로 검증자 등록 (1 트랜잭션)
ITON(ton).approveAndCall(wtonAddress, amount, data);
```

**내부 흐름:**

```
사용자: TON.approveAndCall(wton, amount, data)
                    │
                    ▼
┌─────────────────────────────────────────────────────────────┐
│  WTON 컨트랙트                                               │
│  1. TON → WTON 변환 (1 TON = 1e9 WTON)                      │
│  2. data에서 RAT 주소 추출                                   │
│  3. WTON을 RAT으로 전송                                      │
│  4. RAT.onApprove(owner, wton, wtonAmount, remainingData)   │
└─────────────────────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────────────────┐
│  RAT.onApprove                                               │
│  1. msg.sender == wton 검증                                  │
│  2. remainingData에서 systemConfig 추출                      │
│  3. DepositManager.deposit(layer2, wtonAmount) - RAT 명의    │
│  4. 검증자 등록 정보 저장                                      │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 onApprove 구현

```solidity
/// @notice WTON에서 호출되는 콜백 (TON.approveAndCall 경유)
/// @param owner TON 전송자 (검증자)
/// @param spender RAT 컨트랙트 주소
/// @param amount WTON 양 (27 decimals)
/// @param data systemConfig 주소 (32바이트)
function onApprove(
    address owner,
    address spender,
    uint256 amount,
    bytes calldata data
) external returns (bool) {
    require(msg.sender == wton, "only WTON");

    address systemConfig = address(uint160(uint256(bytes32(data[:32]))));

    // DepositManager에 대리 스테이킹 (RAT 명의)
    _depositToDepositManager(systemConfig, amount);

    // 검증자 등록
    _registerValidatorInternal(owner, systemConfig, amount);

    return true;
}
```

> **구현 상세**: `onApprove` 함수 구현은 [07_rat_implementation.md](./07_rat_implementation.md) 6.1장 참조

## 5. 검증자 담보금 관리

### 5.1 RAT의 대리 스테이킹 메커니즘

검증자 담보금은 **RAT 컨트랙트가 DepositManager에 대리 스테이킹**하는 방식으로 관리됩니다.

**설계 이유:**
- 검증자가 직접 스테이킹하면 임의로 언스테이킹 가능 → 담보금 역할 상실
- RAT이 대리 스테이킹하면 검증자는 출금 불가 → 담보금 보호

**시뇨리지 처리:**
- 유지한 담보금에 대한 시뇨리지 → **TBD** (검증자 탈퇴시 남은 담보금에 대한 시뇨리지만 검증자에게 지급)
- 몰수된 원금 + 몰수된 원금에 대한 시뇨리지 → **TBD** (귀속처 미정)
- 검증자 보상은 별도로 `α · y(x) / n`으로 지급

> **참고:** RAT 명의의 스테이킹은 L2 자격조건(S_i ≥ θ·B_i)에 기여하지 않습니다. S_i는 시퀀서(오퍼레이터) 명의의 스테이킹만 포함합니다.

```
검증자 등록 흐름:
┌─────────────────┐  approveAndCall  ┌─────────────────┐
│    검증자        │ ───────────────► │      WTON       │
│    (TON)        │                   │  TON→WTON 변환  │
└─────────────────┘                   └────────┬────────┘
                                               │ onApprove
                                               ▼
                                      ┌─────────────────┐
                                      │       RAT       │
                                      │   (WTON 수령)   │
                                      └────────┬────────┘
                                               │ deposit(layer2, amount)
                                               ▼
                                      ┌─────────────────┐
                                      │ DepositManager  │
                                      │  (RAT 명의 예치) │
                                      └─────────────────┘

슬래싱 흐름 (C_off 기반):
┌─────────────────────────────────────────────────────────────┐
│  RAT 트리거 시:                                              │
│    - depositedAmount -= C_off                               │
│    - totalBondForRAT += C_off                               │
│    - DepositManager: 변경 없음 (RAT 명의 스테이킹 유지)       │
│                                                             │
│  증거 제출 성공 시:                                          │
│    - depositedAmount += C_off (복구)                        │
│    - totalBondForRAT -= C_off                               │
│                                                             │
│  미응답 시:                                                  │
│    - (아무것도 안 함 - 이미 차감됨)                          │
│    - 잔액 < D_min 이면 즉시 활성 검증자 세트에서 제거        │
│    - 잔액은 검증자가 클레임하여 출금 가능                     │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 출금 금액 계산

```
출금 가능 금액 = depositedAmount × (currentFactor / coinageFactorAtDeposit)
```

- `latestTestEndBlock`: 가장 최근 RAT 테스트의 증거 제출 마감 블록 (테스트 종료일이 지나야 출금 가능)
- `depositedAmount`: 현재 유효 담보금 (슬래싱으로 차감된 후 금액)
- `coinageFactorAtDeposit`: 예치 시점의 coinage factor
- `currentFactor`: 출금 시점의 coinage factor

> **몰수된 담보금 처리**: 몰수된 원금 + 시뇨리지의 사용처는 TBD

## 6. 검증자 비활성화 (탈퇴)

### 6.1 비활성화 조건

- 검증자 본인만 비활성화 가능 (자발적 탈퇴)
- 해당 SystemConfig에서 활성 상태여야 함
- **각 SystemConfig에서 개별적으로 탈퇴** 가능
- 담보금과 미청구 보상은 **별도로 처리**
- **증거제출 기간 중에는 탈퇴 불가**

### 6.2 비활성화 흐름

```
┌─────────────────────────────────────────────────────────────┐
│  1. unregisterValidator(systemConfig) 호출                   │
│     - 특정 L2(SystemConfig)에서만 탈퇴                       │
│     - 증거제출 기간 중이면 실패                               │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 상태 변경                                                │
│     - isActive = false (해당 SystemConfig에서)               │
│     - activeValidators 배열에서 제거 + 인덱스 재정렬          │
│     - validatorPools[systemConfig].activeValidatorCount 감소 │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 담보금/보상 별도 처리                                    │
│     - 담보금: 담보금 출금요청함. 2주뒤, 직접 processUnstake()로 별도 출금 완료해야함.  │
│     - 미청구 보상: claimRewards()로 별도 청구                │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 담보금 출금

검증자 탈퇴 시 DepositManager의 출금 프로세스를 거쳐야 합니다:
1. `requestUnstake()`: 전액 출금 요청 (내부 기록 차감 + DepositManager에 요청)
   - **부분 출금 불가**: 항상 `depositedAmount` 전체를 출금해야 함
2. **2주 대기** (DepositManager의 출금 지연 기간)
3. `processUnstake()`: 검증자가 호출하여 실제 출금 처리 후 검증자에게 전송 (원금 + 시뇨리지)

```
┌──────────┐  requestUnstake()   ┌──────────┐  requestWithdrawal  ┌────────────────┐
│ 검증자    │ ─────────────────► │   RAT    │ ─────────────────► │ DepositManager │
│ (전액만)  │  (전액 출금만)      └──────────┘                     └────────────────┘
└──────────┘
                                      │
                                      │  2주 대기
                                      ▼
┌──────────┐  processUnstake()   ┌──────────┐  processRequest    ┌────────────────┐
│ 검증자    │ ─────────────────► │   RAT    │ ─────────────────► │ DepositManager │
│          │  (출금 처리 요청)    └──────────┘                     └────────────────┘
│          │                              │
│          │                              │ WTON (원금+시뇨리지)
│          │◄─────────────────────────────┘
│ (WTON)   │
└──────────┘
```

> **구현 상세**: `requestUnstake`, `processUnstake` 함수 구현은 [07_rat_implementation.md](./07_rat_implementation.md) 6.7장 참조

## 7. 검증자 보상

### 7.1 보상 공식

**백서 공식 (13)**에 따른 검증자 보상:

```
v_i = (α / n) · y(x)    ... (13) 검증자 보상
```

| 파라미터 | 백서 명시 | 설명 |
|---------|----------|------|
| **α** | ✅ | 검증자 분배 비율 (예: 20%) |
| **n** | ✅ | 활성 검증자 수 (해당 SystemConfig 내) |
| **y(x)** | ✅ | 쌍곡선 포화 함수 결과 |

**핵심 특징 (백서 명시):**
- **SystemConfig별** 활성 검증자가 균등하게 보상 분배 (1/n)
- 담보금 크기와 무관하게 동일 보상
- RAT에 응답하고 활성 상태를 유지해야 보상 수령 자격

### 7.2 보상 분배 흐름

```
특정 L2가 updateSeigniorage() 호출 (SeigManager)
            │
            ▼
┌───────────────────────────────────────┐
│  해당 L2의 시뇨리지 계산               │
│  Seig_i = y(x) · (B̃_i / x)           │
└───────────────────────────────────────┘
            │
            ▼
┌───────────────────────────────────────┐
│  Layer2Manager.transferL2Seigniorage  │
│  (layer2, Seig_i)                     │
│  → OperatorManager로 WTON 전송        │
└───────────────────────────────────────┘
            │
            ▼
┌───────────────────────────────────────┐
│  OperatorManager.receiveL2Seigniorage │
│  - 검증자 수 확인 (0명이면 전액 시퀀서)│
│  - 시퀀서 몫: (1 - α) · S_i         │
│  - 검증자 풀: α · y(x) (전체에서)    │
└───────────────────────────────────────┘
            │
    ┌───────┴───────┐
    ▼               ▼
┌─────────────┐  ┌─────────────────────────┐
│ 시퀀서 몫   │  │ 검증자 몫               │
│ Operator    │  │ RAT 컨트랙트로 전송     │
│ Manager에   │  │ distributeReward() 호출 │
│ 남음        │  └─────────────────────────┘
│ (claimERC20)│              │
└─────────────┘              ▼
                 ┌─────────────────────────┐
                 │ 해당 L2 활성 검증자에게  │
                 │ 균등 분배 (1/n)          │
                 └─────────────────────────┘
```

> **참고**: 검증자가 없으면 `validatorAmount = 0` → 전액 시퀀서 몫

### 7.3 보상 청구

```solidity
// SystemConfig별 보상 청구
IRAT(ratContract).claimRewards(systemConfig);

// 모든 SystemConfig에서 보상 일괄 청구
IRAT(ratContract).claimAllRewards();
```

> **구현 상세**: `distributeReward`, `claimRewards` 함수 구현은 [07_rat_implementation.md](./07_rat_implementation.md) 6.6장 참조

## 8. RAT (Randomized Attention Test)

### 8.1 RAT 개요

RAT는 검증자가 실제로 네트워크를 모니터링하고 있는지 확인하는 무작위 테스트입니다.

**백서 내용 (1.3.1 RAT):**
- RAT는 무작위로 검증자를 선택하여 특정 L2 배치를 검증하도록 요구
- 선택된 검증자는 배치를 확인하고 정확성에 대한 증명(attestation)을 제출해야 함
- 정직하게 응답하면 검증자 수수료(validator fee)를 받고, 미응답 또는 부정직 시 슬래싱
- 게임 이론적으로 설계되어 검증 스킵의 기대 비용이 단기 절감보다 높음

| 항목 | 백서 명시 | 구현 제안 |
|------|----------|----------|
| **목적** | ✅ 검증자의 활성 상태 확인 | - |
| **발행 주체** | ✅ 프로토콜 (무작위) | - |
| **발행 확률** | ✅ π_a (공식 3, 4, 5) | 1% |
| **증거 제출 기간** | ❌ 명시 안됨 | ~24시간 (7200 블록) |
| **미응답 시** | ✅ C_off 슬래싱 | C_off 슬래싱 (D_min 미만 시 즉시 제거) |

### 8.2 RAT 트리거 시점

RAT는 L2 프로포저(시퀀서)가 **Dispute Game을 생성할 때** 트리거됩니다.

```
┌─────────────────────────────────────────────────────────────┐
│  Optimism L2 프로포저 (op-proposer)                          │
│                                                              │
│  1. Output Root 계산                                         │
│  2. DisputeGameFactory.create() 호출                         │
│     └─→ RAT.triggerAttentionTest() 호출                      │
└─────────────────────────────────────────────────────────────┘
```

### 8.3 RAT 흐름 (C_off 기반 선차감-복구 메커니즘)

```
┌─────────────────────────────────────────────────────────────┐
│  1. L2 프로포저가 DisputeGame 생성                           │
│     - triggerAttentionTest(systemConfig, batchIndex, ...)   │
│     - 확률: ratTriggerProbability (1%)                       │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 해당 SystemConfig의 검증자 풀에서 랜덤 선택              │
│     - activeValidators[systemConfig]에서 선택               │
│     - depositedAmount -= C_off                              │
│     - totalBondForRAT += C_off                              │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 검증자 증거 제출 대기                                    │
│     - 제출 기간: evidenceSubmissionPeriod (~24시간)          │
└─────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
    ┌─────────────────┐             ┌─────────────────┐
    │  증거 제출       │             │  미응답         │
    │  submitEvidence │             │  deadline 경과  │
    └─────────────────┘             └─────────────────┘
              │                               │
              ▼                               ▼
    ┌─────────────────┐             ┌─────────────────────────┐
    │  depositedAmount│             │  (아무것도 안 함)        │
    │  += C_off       │             │  잔액 >= D_min → 활성유지│
    │  totalBondForRAT│             │  잔액 < D_min → 즉시 제거│
    │  -= C_off       │             │  (잔액은 클레임 가능)   │
    └─────────────────┘             └─────────────────────────┘
```

### 8.4 챌린지 승리 시 담보금 복구

검증자가 프로포저의 잘못된 증거에 대해 챌린지를 제기하고 **게임에서 승리**하면, FaultDisputeGame에서 `resolveClaim`을 호출하여 담보금을 복구합니다.

```
┌─────────────────────────────────────────────────────────────┐
│  1. 프로포저가 잘못된 Output Root 제출                        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 검증자(챌린저)가 FaultDisputeGame에서 챌린지 제기         │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 게임 해결 - 검증자(챌린저) 승리                           │
│     - FaultDisputeGame.resolveClaim() 호출                   │
│     - resolveClaimRat(winner) → RAT.resolveClaim(winner)    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  4. RAT에서 담보금 복구                                       │
│     - depositedAmount += C_off                               │
│     - totalBondForRAT -= C_off                               │
└─────────────────────────────────────────────────────────────┘
```

> **구현 상세**: RAT 트리거, 증거 제출, resolveClaim 함수 구현은 [07_rat_implementation.md](./07_rat_implementation.md) 6.2~6.5장 참조

## 9. 거버넌스 파라미터

| 파라미터 | 백서 명시 | 설명 |
|---------|----------|------|
| **maxValidators** | ✅ (H_max) | 검증자 최대 수 (= 최대 챌린저 수) |
| **attentionCost** | ✅ (c_m) | 에폭당 attentiveness 유지 비용 |
| **validatorCount** | ✅ (N) | 검증자 수 |
| **ratTriggerProbability** | ✅ (π_a) | RAT 트리거 확률 |
| **slashingPenalty** | ✅ (C_off) | 오프라인 시 슬래싱 페널티 |
| **minimumThreshold** | ✅ (D_min) | 최소 담보금 임계값 |
| **validatorBuffer** | ✅ (Δ_validator) | 검증자가 제공하는 추가 담보금 |
| **evidenceSubmissionPeriod** | ❌ | 증거 제출 기간 |
| **validatorDistributionRatio** | ✅ (α) | 검증자 분배 비율 |

**최소 슬래싱 페널티는 백서 공식 (4)로 계산:**
```
C_off ≥ (c_m · N) / π_a
```

**실제 담보금은 백서 공식 (5)로 계산:**
```
D_validator = C_off + Δ_validator
```

## 10. 검증자 운영 가이드

### 10.1 검증자가 해야 할 일

| 작업 | 빈도 | 설명 |
|------|------|------|
| **등록한 L2 배치 모니터링** | 상시 | 등록한 SystemConfig의 DisputeGame 생성 감시 |
| **RAT 증거 제출** | RAT 트리거 시 | 증거 제출 기간 내 submitEvidence() 호출 |
| **보상 청구** | 원하는 시점 | claimRewards(systemConfig) 또는 claimAllRewards() |
| **담보금 관리** | 필요 시 | addStake() 또는 unregisterValidator() |

### 10.2 주의사항

1. **24/7 가용성**: RAT는 DisputeGame 생성 시 발생하므로 모니터링 시스템 항상 가동
2. **증거 제출 기간 준수**: ~24시간 내 미제출 시 C_off 슬래싱
3. **담보금 관리**: 잔액이 D_min 미만이 되면 즉시 활성 검증자에서 제거됨 (재등록 필요)
4. **가스비 준비**: 증거 제출 트랜잭션을 위한 ETH 보유
5. **이벤트 구독**: AttentionTriggered 이벤트 구독 및 알림 설정 권장
6. **복수 L2 관리**: 여러 SystemConfig에 등록한 경우 각각 모니터링 필요

### 10.3 검증자 클라이언트 구현 가이드

```typescript
// 이벤트 리스너 예시
ratContract.on("AttentionTriggered", async (testId, systemConfig, layer2, validator, batchIndex) => {
    if (validator === myAddress) {
        // 해당 배치 데이터 조회
        const batchData = await fetchBatchData(systemConfig, batchIndex);

        // 증거 제출
        await ratContract.submitEvidence(systemConfig, batchIndex, batchData);
    }
});
```
